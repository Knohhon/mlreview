# Разработка: спецификация → тесты → код → проверки

Шаги идут строго по порядку. Не переходить к следующему, пока не закончен предыдущий.

## 1. Зафиксировать ожидаемое поведение

1. Найти опору в требованиях. Не читать `docs/dialogs/`.
   ```bash
   grep -n "FR-D01\|S02\|B08" docs/MLReview-analysis.md docs/User-cases-MLReview.md
   ```
   Проверить уровень (L0/L1/…): то, что выше текущего уровня (сейчас L0), не делать без явной просьбы.
2. Создать или обновить `docs/specs/<имя>.md` по шаблону из `docs/specs/README.md`:
   - пункты поведения `B1…` в форме «дано · когда · тогда» с конкретными входами и выходами;
   - пункты деградации `E1…` — неполный контракт, нет LLM, плохие входы (сценарии X1–X6): инструмент явно сообщает, что не сделал и почему;
   - «вне рамок»;
   - соответствие пунктов и будущих тестов.
3. Если поведение неоднозначно (пороги, формат вывода, интерфейс), показать спецификацию пользователю и согласовать до тестов.

## 2. Написать тесты под поведение

1. Тесты в `tests/test_<модуль>.py`; докстринг теста ссылается на пункт спецификации: `"""B1: …"""`.
2. Каждый пункт B*/E* покрыт хотя бы одним тестом. Детерминированность: фиксированные сиды (NFR-05). Сеть в тестах заблокирована (`tests/conftest.py`), данные — маленькие синтетические фикстуры в коде теста или в каталоге tests/data (создать при необходимости).
3. Запустить новые тесты и убедиться, что они **падают по правильной причине** (нет функции / неверный результат), а не из-за ошибки в самом тесте:
   ```bash
   python -m pytest tests/test_<модуль>.py -q
   ```
   Сообщить пользователю: «тесты написаны, красные — ожидаемо».

## 3. Реализовать

1. Минимальный код, чтобы тесты стали зелёными. Не менять тесты под реализацию; если тест оказался неверным — сначала поправить спецификацию, затем тест, и сказать об этом.
2. Соблюдать инварианты из CLAUDE.md: ядро без фреймворков и трекеров (проверяет `tests/test_architecture.py`), факты отдельно от LLM, явная деградация.
3. Докстринг модуля ссылается на закрываемые FR-*.

## 4. Проверить

Запустить скилл `check` (или те же команды вручную) и довести до зелёного:
```bash
python -m ruff check . && python -m ruff format --check . && python -m pytest -q
```
Хук `Stop` повторит эти проверки в конце хода; хук после правок проверяет каждый изменённый `.py`.

## 5. Актуализировать документацию

По скиллу `docs-sync`: CLAUDE.md и скиллы поправить самому, по README и `docs/` — перечислить несоответствия и предложить правки. Хук `Stop` напомнит об этом, если файлы изменились.

## 6. Отчитаться

Кратко: какая спецификация, какие тесты (сколько и что покрывают), что реализовано, результат проверок с цифрами, что актуализировано в документации и какие правки предложены. Если что-то осталось красным или отложено — сказать прямо.
