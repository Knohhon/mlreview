# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Проект

MLReview — open-source ассистент-критик для ML-экспериментов. Требования (с идентификаторами FR-*/NFR-*), критерии приёмки и этапы разработки описаны в `docs/MLReview-analysis.md` — это основной источник контекста о проекте. Пользовательские сценарии — в `docs/User-cases-MLReview.md`.

Статус: уровень L1 реализован (Must и Should; кандидаты S18, S21/B13, S30 не делались). Всё описано в спецификациях `docs/specs/`; быстрый старт — `docs/quickstart.md`. Карта кода:

- **Ядро (`src/mlreview/core/`):** спецификация задачи FR-C01 (`task_spec.py`, `task-spec.md`; раздел `metrics:` — `metrics.md`), контракт прогона FR-C02 (`run_contract.py`, `run-contract.md`) с хешем данных FR-C04 (`data-version.md`) и сведениями о модели FR-C07 (`model_info.py`, `model-info.md`: класс, библиотека, семейство, важности признаков; пробел `model`), находки и отпечатки (`findings.py`, `review.md`), рабочее пространство `.mlreview/` (`workspace.py`) и SQLite-хранилище находок, прогонов и журнала FR-C05/C06/R05 (`store.py`, `findings-store.md`, `journal.md`).
- **Адаптеры (`src/mlreview/adapters/`):** MLflow FR-C03 (`mlflow_adapter.py`, `mlflow-adapter.md`; модель — из тегов `mlreview.model.*` или `estimator_class` автологирования sklearn, у Pipeline — последний шаг `steps`; `mlflow` импортируется лениво; ручная проверка — `docs/manual-testing/mlflow-adapter.md`, после изменений адаптера пройти её и дописать строку в журнал в конце файла), локальные файлы (`files_adapter.py`, `files-adapter.md`), выбор по ссылке — каталог или id MLflow (`base.py`).
- **Анализаторы (`src/mlreview/analyzers/`):** единый интерфейс и реестр FR-E01 (`registry.py`, `builtin.py`, `analyzers.md`); группы `data` (FR-D03), `segments` (FR-D02, поправка Холма), `metrics` (FR-D01 сравнение, пригодность метрик B05 `suitability.py`, сиды FR-D05 `seeds.py` — по всем метрикам задачи, калибровка и расхождение FR-D08 `calibration.py`), `model` (FR-D11: проверки плейбуков, `src/mlreview/playbooks/runner.py`), `curves` (FR-D04), `process` (FR-D06: B07, B11 — смена семейства модели считается одним изменением, повтор валидации). Бутстрап — 1000 выборок, сид 0; ROC AUC на выборках — через веса повторов (`auc_sampler`, NFR-06). Числа в `facts` округлены до 6 знаков, сообщения строятся из них.
- **Плейбуки (`src/mlreview/playbooks/`):** FR-E02 (внутренний) и FR-D11, `playbooks.md`: каталог `<id>/playbook.yaml` (pydantic-манифест `loader.py`: применимость, `detect` класс → семейство, алиасы гиперпараметров `params`, пороги, тексты, `overrides` подсказок общих проверок) + необязательный `checks.py` с `run(ctx: PlaybookContext)`; семейство и гиперпараметры — `resolve.py` (`resolve_family`, `model_params`), группа ревью `model` и подсказки — `runner.py`. Встроенные: `linear`, `neighbors`, `trees` (распознаёт и ансамбли: bagging, бустинги sklearn/LightGBM/XGBoost/CatBoost). Тесты подменяют набор через `loader.builtin_playbooks`.
- **Метрики (`src/mlreview/metrics/`):** каталог (`catalog.py`), реализации на numpy, сверенные со scikit-learn (`kernels.py`, их исходник копирует экспорт), метрики задачи для анализаторов (`library.py`), рекомендации (`advisor.py`), юнит-тесты метрик (`testing.py`), экспорт (`export.py`) — FR-M01–M05, `metrics.md`.
- **LLM (`src/mlreview/llm/`):** настройки (`config.py`; по умолчанию `provider: none`), один транспорт на stdlib urllib (`transport.py`; тесты подменяют `get_transport`), провайдеры Anthropic (модель по умолчанию `claude-opus-5-5`, серверный fallback при отказе) и OpenAI-совместимый для локальных моделей (`providers.py`), сверка чисел и ссылок FR-L02/L03 (`grounding.py`), контекст без сырых данных NFR-04 (`context.py`), вызов и журнал стоимости NFR-08 (`assistant.py`), сценарии гипотез и `ask` (`service.py`) — `llm.md`; ручная проверка с настоящими провайдерами — `docs/manual-testing/llm.md`.
- **Интерфейсы:** CLI — пакет `src/mlreview/cli/` (`review`, `diagnose data|segments|model|curves|process`, `metrics init|test|export|list`, `ask`, `spec`, `contract`, `playbooks list`, `init`, `findings`, `dismiss`, `journal`, `watch`, `mcp`); Python API FR-R03 (`api.py`, `api.md`), общее представление отчёта (`reporting.py`), проактивный режим FR-R04 (`proactive.py`, `proactive.md`), MCP-сервер FR-R02 на SDK `mcp` 2.x (`src/mlreview/mcp_server/`, extra `mcp`, `mcp-server.md`).
- **Бенчмарк:** пакет `benchmark/` в корне (вне `mlreview`, со sklearn; `docs/specs/benchmark.md`): `python -m benchmark` — 21 дефект L0–L1 и гейт L1 (Q1 ≥ 70%, Q2 ≤ 1); `python -m benchmark --perf` — NFR-06 (100 тыс. примеров ≤ 120 с). Тест `tests/test_benchmark.py` — самый долгий (~45 с).

Следующие шаги — уровень L2 (≥4 типов задач, W&B, публичные плагины и плейбуки, B04/B06/B09/B10); не начинать без запроса. Первые целевые задачи — классификация и регрессия на табличных данных (линейные модели), первый трекер — MLflow. В работе по запросу (L2): модели kNN и деревья — сведения о модели FR-C07 и формат плейбуков YAML + Python-проверки (FR-E02, внутренний) — сделаны; дальше проверки плейбуков `neighbors` и `trees` (FR-D11) с дефектами бенчмарка B14–B18; ансамбли и бустинги — следующим шагом, детект их классов и алиасы гиперпараметров закладываются в плейбук деревьев.

## Команды

```bash
pip install -r requirements.txt         # окружение разработки: пакет с extras mlflow, mcp, dev + scikit-learn для бенчмарка
pip install -e ".[dev]"                 # минимальная установка: пакет и dev-инструменты (Python 3.10+); тесты адаптера MLflow пропускаются
ruff check .                            # линтер
ruff format .                           # форматирование
pytest                                  # все тесты
pytest tests/test_cli.py::test_version  # один тест
python -m mlreview --help               # запуск CLI (или `mlreview`)
python -m benchmark                     # приёмочный бенчмарк L0–L1 (нужен scikit-learn)
python -m benchmark --perf              # NFR-06: ревью 100 тыс. примеров без LLM ≤ 2 мин
```

Перед коммитом `ruff check .`, `ruff format --check .` и `pytest` должны проходить (скилл `check`). CI (`.github/workflows/ci.yml`) запускает то же самое (ставит `.[dev,mlflow,mcp]`, чтобы адаптер и MCP-сервер проверялись; scikit-learn приходит зависимостью mlflow, поэтому бенчмарк в CI тоже прогоняется, а на 3.13 — ещё `python -m benchmark --perf`), тесты — на Python 3.10–3.13, поэтому синтаксис должен быть совместим с 3.10. Настройки ruff — в `pyproject.toml` (`[tool.ruff]`), длина строки 100. Версия пакета задаётся в `src/mlreview/__init__.py` (hatch читает её оттуда).

## Порядок разработки (обязательный)

Любая разработка — фича, анализатор, команда, исправление бага — идёт по скиллу `develop`:

1. **Спецификация.** Ожидаемое поведение фиксируется в `docs/specs/<имя>.md` (шаблон — `docs/specs/README.md`): пункты B*/E* «дано · когда · тогда» со ссылками на FR/NFR/S/B.
2. **Тесты.** Под каждый пункт — тест, докстринг которого начинается с номера пункта (`B1: …`); убедиться, что новые тесты красные по правильной причине.
3. **Код.** Минимальная реализация до зелёных тестов; тесты под код не подгоняются.
4. **Проверки.** `ruff check`, `ruff format --check`, `pytest` (скилл `check`).
5. **Документация.** Актуализировать CLAUDE.md и скиллы; по остальным markdown — предупредить о несоответствиях и предложить правки (скилл `docs-sync`, `python .claude/hooks/doc_sync.py report`).

Хуки в `.claude/settings.json` (скрипты в `.claude/hooks/`, их тоже проверяет ruff):
- после каждой правки `.py` — `ruff check` и `ruff format --check` этого файла; ошибки возвращаются Claude;
- в конце хода, если менялся код, — полный `ruff check`, `ruff format --check` и `pytest`; при падении Claude должен исправить или объяснить (например, «тесты написаны, реализации ещё нет»);
- в конце хода, если с прошлой актуализации изменились файлы, — `doc_sync.py` возвращает Claude список изменений и автоматические находки (битые ссылки на пути, неизвестные FR/NFR); дальше по скиллу `docs-sync`: CLAUDE.md, скиллы и настройки Claude актуализирует сам, по README и `docs/` — предупреждает о несоответствиях и предлагает правки, не применяя их без согласия (спецификация — `docs/specs/doc-sync.md`, снимок — `.claude/state/`, в git не попадает);
- в конце хода и сессии — сохранение диалога в `docs/dialogs/claude-<дата>-<сессия>.md`;
- перед командами Bash — блокировка чтения `docs/dialogs/`.

Тестовые стражи (`docs/specs/invariant-guards.md`): `tests/test_architecture.py` падает, если код вне `src/mlreview/adapters/` импортирует фреймворк обучения или трекер; `tests/conftest.py` блокирует сеть во всех тестах и переводит каждый тест во временный текущий каталог без `MLREVIEW_HOME` (тесты не видят `.mlreview` разработчика). Там же фикстура `mlflow_store` — локальный sqlite-трекер MLflow во временном каталоге (без пакета mlflow тест пропускается). Общие фабрики синтетических прогонов — `tests/_factories.py`, поддельный транспорт LLM для аудита исходящих запросов — `tests/_fake_llm.py`.

## Архитектура

- `src/mlreview/` — пакет (src-layout): `core` (спецификация задачи, контракт прогона, сведения о модели, находки, рабочее пространство, хранилище находок и журнал), `adapters` (MLflow, файлы), `analyzers`, `metrics`, `llm`, `playbooks` (плейбуки по семействам моделей), `mcp_server`, `cli` (пакет), `api.py`, `reporting.py`, `proactive.py`. Докстринг каждого подпакета ссылается на требования FR-*, которые он закрывает; в новом коде следовать этой привычке.
- Поток данных: адаптер → контракт прогона → детерминированные анализаторы → *находки* (важность, доказательства) → хранилище находок → CLI / MCP / проактивное ревью. LLM-слой только синтезирует гипотезы поверх находок.
- Ключевые инварианты (проверяются тестами по мере реализации):
  - **NFR-01:** ядро не импортирует фреймворки обучения и трекеры (страж — `tests/test_architecture.py`); в `[project] dependencies` только вычислительные библиотеки и ввод-вывод данных (numpy, scipy, pandas, pyyaml, pydantic, pyarrow — parquet в адаптере файлов); интеграции — через extras в `pyproject.toml` (`mlflow` — только в `src/mlreview/adapters/`, `mcp` — только в `src/mlreview/mcp_server/server.py`, лениво); LLM — без SDK, через stdlib; scikit-learn — только для бенчмарка (`requirements.txt`).
  - **FR-L02:** каждое число в ответе LLM берётся из фактов анализаторов, каждое утверждение ссылается на находку.
  - **NFR-03:** всё детерминированное работает без LLM; тесты проходят офлайн (сеть заблокирована в `tests/conftest.py`).
  - **NFR-04:** данные не покидают машину; во внешнюю LLM — только агрегаты и явно выбранные примеры.
  - **NFR-05:** факты воспроизводимы — сиды (например, бутстрапа) фиксированы.

## Предметная модель и правила поведения

Источник — `docs/MLReview-analysis.md` (требования) и `docs/User-cases-MLReview.md` (сценарии S01–S30, сквозные X1–X6).

- **Термины:** *спецификация задачи* (YAML: тип задачи, выход, цена ошибок, сегменты, `split_strategy`, версия данных, известные проблемы); *контракт прогона* (предсказания, метки, id и метаданные примеров, конфиг, кривые, версия данных); *анализатор* (детерминированная проверка → факты); *находка* (severity, доказательства — например id примеров, статус: новая/принята/отклонена/исправлена); *плейбук* (пакет знаний по типу задачи).
- **Объём L0–L1 (реализован):** L0 — FR-C01–C03 (MLflow), FR-D01–D03, FR-R01; L1 — FR-C03 (файлы), FR-C04–C06, FR-M01–M05, FR-D04–D08, FR-R02–R05, FR-L01–L03, FR-E01 (внутренний). Ловятся дефекты бенчмарка B01, B02, B03, B05, B07, B08, B11, B12. Остальное (FR-M06, FR-D09/D10, FR-R06, FR-L04, FR-E02/E03, B04/B06/B09/B10, W&B) — L2+; не реализовывать без запроса. Не проверены автоматически: NFR-01 на трёх фреймворках (в бенчмарке только scikit-learn), NFR-02 на реальных провайдерах (ручная проверка `docs/manual-testing/llm.md`), NFR-07 (замер на пользователях).
- **Явная деградация (X1–X6):** не падать и не молчать — сообщать, что не сделано и почему. Неполный контракт → перечислить пропущенные анализаторы и недостающие поля, остальные работают. Без LLM команды вроде `ask` отвечают «требует LLM», а не падают. LLM-ответ с числом вне фактов блокируется. Отклонение critical-находки требует причины.
- **Инструмент не применяет изменения сам** — только предлагает изменение и (различающий) эксперимент.
- Подкоманды и флаги в сценариях (`metrics init`, `diagnose data`, `dismiss`, `--format json --fail-on critical` и т. п.) иллюстративные, а не утверждённый интерфейс. Предложения из раздела «Сводка и предложения в требования» (S18–S30, B13, повышение FR-C06 до Must и др.) ещё не приняты в требования.
- Открытые вопросы, от которых зависит дизайн: формат плейбука (только YAML или YAML + Python-проверки); как ловить B04/B10 (анализ кода пайплайна или описание в спецификации); сбор сигнала полезности (телеметрия или опросы).

## Соглашения

- Документация, докстринги и сообщения пользователю пишутся по-русски (поэтому в ruff отключены RUF001–RUF003).
- `README.md` — только о продукте: назначение, возможности, статус, планы, установка и разработка самого пакета. Настройки и процесс работы с Claude (CLAUDE.md, `.claude/`, скиллы, хуки, `docs/specs/` как часть процесса, диалоги) в README не добавлять и не предлагать — они описаны здесь.

## Ограничения

- **Не читать файлы диалогов.** Папка `docs/dialogs/` содержит сохранённые диалоги (переписку), а не документацию проекта. Не открывать, не искать по ним и не использовать их содержимое как контекст — ни через Read/Grep/Glob, ни через команды оболочки (`cat`, `grep`, `head` и т. п.). Исключение — только прямая просьба пользователя прочитать конкретный файл диалога; технически Read этой папки запрещён в `.claude/settings.json`, так что для этого пользователь должен сам снять запрет.
- Рекурсивный поиск в оболочке — только с `--exclude-dir=dialogs` или по конкретным путям (`src/`, `tests/`); `.ignore` исключает папку из ripgrep и поиска Claude Code.
- Диалоги с Claude записываются в `docs/dialogs/` автоматически хуком; вручную их не писать и не править (Edit/Write папки запрещены).
- Перемещать, переименовывать или удалять файлы в `docs/dialogs/` можно, не открывая их содержимого (`ls`, `mv`, `rm`, `git add/mv/rm` хук разрешает).
