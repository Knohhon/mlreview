# MLReview

**Open-source ассистент-критик для ML-экспериментов.** Помогает спроектировать метрики под задачу, интерпретировать результаты прогонов и найти проблемы в данных, экспериментах и выводах. Работает и по запросу, и сам — после каждого прогона.

> **Статус:** стадия проектирования. Зафиксированы видение, требования и критерии приёмки; есть скелет Python-пакета и первая часть прототипа — спецификация задачи с проверкой (`mlreview spec validate`); анализаторов пока нет. См. [«Текущее состояние»](#текущее-состояние).

---

## Зачем

Инструменты вокруг обучения моделей уже хорошо закрывают две вещи: **хранение** прогонов (трекеры экспериментов) и **автоматическую сборку** пайплайнов (AutoML, агенты «дал задачу — получил систему»). Но самые затратные по времени вопросы остаются на инженере:

- **Какие метрики правильные для этой задачи?** Каждый раз их приходится придумывать заново, и легко выбрать метрику, которая обманывается тривиальным бейзлайном или слишком шумная, чтобы различать модели.
- **Что на самом деле произошло в эксперименте?** Средняя метрика выросла — а на каком сегменте стало хуже? Улучшение реальное или в пределах разброса по сидам?
- **Где ошибка?** Утечка между сплитами, сравнение прогонов на разных версиях данных, три изменения в одном эксперименте, переобучение на валидации.

MLReview — это **слой рассуждения поверх истории проекта, с человеком в контуре**. Ближе к код-ревью, чем к автопилоту: инструмент не обучает модели и не меняет код сам, а находит проблемы, объясняет их и предлагает следующий шаг.

## Ключевые идеи

**Описывать задачу, а не модель.** Метрики и большая часть диагностики вытекают из свойств задачи и данных, а не из архитектуры. Поэтому в центре два контракта:

- **Спецификация задачи** — что на входе и выходе, цена разных ошибок, как используются предсказания, важные сегменты, стратегия сплита, известные проблемы данных.
- **Контракт прогона** — предсказания, метки, идентификаторы и метаданные примеров, конфиг, кривые обучения, версия данных. Модель для инструмента — чёрный ящик: классический алгоритм, нейросеть или дообученная LLM обрабатываются одинаково.

**Факты отдельно от интерпретаций.** Детерминированные анализаторы считают цифры и производят *находки* с доказательствами. Языковая модель (опционально) только синтезирует гипотезы поверх этих находок — каждое число в её ответе берётся из фактов, каждое утверждение ссылается на находку. Это главная защита от уверенно сгенерированных объяснений шума.

**Работает без LLM.** Все детерминированные проверки доступны офлайн и без внешних сервисов. LLM-слой подключается по желанию, провайдер меняется конфигурацией, поддерживаются локальные модели.

**Приватность по умолчанию.** Данные не покидают машину. Во внешнюю модель, если она подключена, уходят только агрегаты и явно выбранные примеры.

**Один движок — два режима.**

```
события (прогон завершён / данные изменились / спецификация изменилась)
        │
        ▼
  анализаторы → находки (важность, доказательства) → хранилище находок
        │                                               │
  проактивно: короткое ревью,                    реактивно: командная строка,
  только выше порога важности                    программный интерфейс, агенты
```

Проактивный режим фильтрует находки по важности, не повторяет одно и то же и учитывает пометку «не важно».

## Возможности (целевые)

### Проектирование метрик
- Диалог о контексте решения: какая ошибка дороже, нужен порог или ранжирование, важна ли калибровка, какие сегменты критичны.
- Подбор кандидатов из библиотеки метрик с обоснованием и известными ловушками.
- **Юнит-тесты метрик:** отличает ли метрика хорошую модель от тривиального бейзлайна, не обманывается ли вырожденным решением, насколько она шумная на вашем размере теста, какой минимальный эффект она способна различить.
- Экспорт итоговой спецификации метрик в исполняемом виде.

### Диагностика и интерпретация
- Сравнение прогонов с доверительными интервалами и значимостью.
- Срезы: сегменты хуже среднего и регрессии по сегментам между прогонами.
- Проверки данных: пересечения и дубли между сплитами, временная утечка, подозрительно сильные признаки.
- Анализ кривых обучения: переобучение, недообучение, нестабильность.
- Разброс по сидам и предупреждение «улучшение в пределах шума».
- Логические проверки процесса: несколько изменений за раз, сравнение на разных версиях данных, многократное использование одной валидации.
- Гипотезы о причинах со ссылками на факты и **различающий эксперимент** — тот, который отделит одну гипотезу от другой, а не просто «попробуй ещё».

### Память проекта
- Журнал гипотез, экспериментов, выводов и решений, связанных друг с другом: что уже пробовали и почему отказались.

### Расширяемость
- Анализаторы как плагины с единым интерфейсом.
- **Плейбуки** — пакеты знаний по типу задачи (метрики, типичные сбои, проверки), подключаемые без изменения ядра. Это основная точка вклада сообщества.

### Чем MLReview не является
- Не трекер экспериментов — подключается к существующим.
- Не AutoML и не обучает модели.
- Не инструмент оценки LLM-приложений (на ранних уровнях).
- Не применяет изменения сам — только предлагает.

## Для кого

| Группа | Что получает |
| --- | --- |
| Соло ML-инженер | Метрики под задачу, ревью после прогона, ответ на «почему хуже» |
| Исследователь | Проверка значимости, «рецензия» серии экспериментов: недостающие бейзлайны и абляции |
| Джун / мидл | Встроенный ревьюер, который ловит классические ошибки и объясняет, что с ними делать |
| Доменный специалист | Метрики через вопросы о бизнес-контексте, без знания ML-терминологии |
| Контрибьютор | Возможность добавить анализатор или плейбук своей области без погружения в ядро |
| Команды и организации | Общая память проектов, дайджесты, отчёты валидации (в перспективе, см. «Планы») |

## Планы

Продукт развивается уровнями; переход на следующий возможен только после прохождения гейта с измеримыми критериями.

| Этап | Уровень | Что делаем | Гейт выхода |
| --- | --- | --- | --- |
| 0 · Discovery | — | Интервью с 5–10 инженерами и исследователями, выбор 1–2 типов задач | Большинство опрошенных называют метрики или интерпретацию главной потерей времени |
| 1 · Прототип | L0 | Использование на собственных проектах: 1 тип задачи, 1 трекер, командная строка, 5–7 анализаторов, первый бенчмарк | Находится ≥50% внедрённых дефектов, ни одного выдуманного числа, время на метрики сокращается ≥30% |
| 2 · MVP (alpha) | L1 | Публичный релиз: модуль метрик, диагностика с гипотезами, ревью после прогона, интерфейс для агентов, работа без LLM | ≥70% дефектов, ≤1 ложной критичной находки на чистый проект, установка ≤15 мин, ≥10 внешних пользователей |
| 3 · v1.0 | L2 | ≥4 типов задач, ≥2 трекера, публичные плагины и плейбуки, программный интерфейс, открытый бенчмарк | ≥85% дефектов, стабильные форматы, ≥10 внешних контрибьюторов |
| 4 · Командный пилот | L3 | Общая память проектов, дайджесты, отчёты валидации, развёртывание внутри организации | ≥3 из 5 пилотных команд продолжают использование через 3 месяца |

Модель распространения — **open core**: всё, что нужно одному человеку на одном проекте (ядро, анализаторы, метрики, LLM-слой, плейбуки), остаётся открытым. Вся командная часть (общая память проектов, дайджесты, ревью экспериментов, отчёты валидации, self-hosted и SSO) — коммерческий слой и в открытое ядро не входит. Нахождение ошибок за плату не прячется.

### Как мы поймём, что инструмент работает

Основа приёмки — **бенчмарк с внедрёнными дефектами**: проекты на публичных датасетах в чистой версии и в версиях с одним известным дефектом (дубли между сплитами, временная утечка, утечка таргета, неподходящая метрика, «улучшение» в пределах шума и др.). Чистые версии измеряют ложные срабатывания, версии с дефектами — долю найденного. Результаты по версиям будут публиковаться здесь.

Жёсткое правило для любого релиза: **ни одного числа в ответе LLM, которого нет в фактах анализаторов.**

### Принятые решения

- **Первые типы задач** — классификация и регрессия на табличных данных; первый целевой класс моделей для прототипа и бенчмарка — линейные модели. Ядро при этом не зависит от модели.
- **Первый трекер** — MLflow, в том числе с учётом развёртывания (self-hosted); W&B — позже.
- **Граница open core** — вся командная часть коммерческая; в открытом ядре её нет.
- **Лицензия** — Apache-2.0.

### Открытые вопросы

- Как собирать сигнал полезности находок в open source: opt-in телеметрия или опросы?
- Как ловить ошибки в пайплайне (препроцессинг на всём датасете, аугментации на валидации): анализом кода или явным описанием пайплайна в спецификации?
- Формат плейбука: только данные или данные плюс исполняемые проверки?

## Разработка

Нужен Python 3.10+.

```bash
pip install -r requirements.txt   # полное окружение L0
pip install -e ".[dev]"           # минимальное: пакет и инструменты разработки
ruff check . && ruff format --check .
pytest
```

Код пакета — в `src/mlreview/`, тесты — в `tests/`. Для автоматической проверки перед коммитом: `pre-commit install`.
