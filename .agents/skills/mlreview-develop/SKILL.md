# Разработка MLReview

Прочитать корневой AGENTS.md и профильную спецификацию в docs/specs/.
Опору FR/NFR искать в docs/MLReview-analysis.md, сценарии — в
docs/User-cases-MLReview.md; архив docs/dialogs/ не использовать.

1. Зафиксировать ожидаемое изменение пунктами B*/E* «дано · когда · тогда»
   в существующей спецификации или новой по шаблону docs/specs/README.md.
   Не начинать дополнительные задачи L2 без запроса.
2. Написать тесты на поведение, включая деградацию при неполном контракте.
   Докстринги начинаются с номера пункта спецификации. Для прогонов использовать
   tests/_factories.py, для внешнего LLM — tests/_fake_llm.py.
3. Запустить новые тесты до реализации: убедиться, что падение связано с требуемым
   поведением, а не ошибкой окружения. Затем реализовать и повторить профильные тесты.
4. Сохранить детерминированность и офлайн-режим; не обходить архитектурные стражи,
   grounding и изоляцию тестов. Обновить связанные CLI/API/MCP, если меняется контракт.
5. Выполнить проверки из mlreview-check. При изменении анализаторов или плейбуков
   применить mlreview-analyzer; при изменении численных методов проверить бенчмарк.
6. Сверить документацию по mlreview-docs-sync. Отчитаться об изменённом поведении,
   проверках и оставшихся ограничениях. Не выдавать skipped за выполненную проверку.
