# Работа Codex в MLReview

## Контекст и границы

MLReview — ассистент-критик ML-экспериментов: адаптер → контракт прогона →
детерминированные анализаторы → находки → хранилище → CLI / API / MCP / LLM.
Уровень L1 реализован; задачи L2 и командные коммерческие функции начинать только
по запросу. Продукт предлагает эксперименты, но сам не обучает и не изменяет модели.

Требования: `docs/MLReview-analysis.md`; сценарии: `docs/User-cases-MLReview.md`.
Поведение модулей: `docs/specs/`; шаблон: `docs/specs/README.md`.
`README.md` и `docs/quickstart.md` описывают установку и использование.
`CLAUDE.md` содержит дополнительную карту проекта; настройки `.claude/` относятся
к Claude Code. Не переносить его события и разрешения в Codex без проверки формата.

Пользовательские изменения сохранять. Перед правками проверить `git status --short`.
Не читать, не искать и не индексировать содержимое `docs/dialogs/` — это архив
переписки, а не документация. Общая просьба изучить проект не отменяет это правило.
Для поиска использовать `rg` с `.ignore` или конкретные каталоги исходников и тестов;
не обходить исключение через `rg --no-ignore`, `git show` или чтение из Python.
Не сохранять переписку автоматически и не трогать рабочие данные `.mlreview/`,
`mlruns/`, `mlartifacts/`, `.env` без необходимости для задачи.

## Разработка и стиль

- Общение, документация, докстринги и сообщения продукта — по-русски;
  Python-идентификаторы — по-английски. Python 3.10–3.13, строки до 100 символов,
  формат и правила Ruff определены в `pyproject.toml`; новые файлы UTF-8, LF.
- Изменение поведения: сначала соответствующая спецификация с пунктами B*/E*
  «дано · когда · тогда», затем тесты с номерами пунктов в докстрингах, затем код.
  До реализации проверить, что новый тест падает по ожидаемой причине.
  Для настройки агента и мелких правок текста достаточно проверки формата и ссылок.
- Исправлять причину ошибки, не подгонять тест под реализацию. Использовать
  `tests/_factories.py` для синтетических прогонов, `tests/_fake_llm.py` для LLM.
- Обновлять `AGENTS.md` и затронутые скиллы при изменении рабочего процесса.
  Спецификации обновлять в рамках разработки. Внешнюю документацию менять, когда
  это входит в запрос; иначе перечислить конкретные расхождения и предлагаемые правки.
  Настройки агентов описывать здесь, а не в продуктовом README.

## Инварианты

- NFR-01: фреймворки обучения и трекеры не импортировать вне `adapters/`.
  Интеграции — extras и ленивые импорты. `mcp` загружается в
  `src/mlreview/mcp_server/server.py`; sklearn нужен тестам/бенчмарку, не ядру.
- FR-L02/L03: числа LLM берёт из `Finding.facts`, утверждения привязывает к находкам;
  проверку grounding не обходить. Транспорт LLM — stdlib, тесты подменяют транспорт.
- NFR-03/04: детерминированное ревью работает без LLM и сети; наружу передаются
  агрегаты и явно выбранные примеры. Не отправлять сырые данные и секреты.
- NFR-05: фиксировать генераторы случайных чисел; для существующего бутстрапа
  приняты 1000 выборок и seed 0. Факты округляются до 6 знаков, тексты строятся из них.
- Неполный контракт или ошибка отдельного анализатора дают явный `Skipped`,
  остальные проверки продолжаются. Без LLM сообщать о недоступной функции.
- `tests/conftest.py` запрещает сеть и изолирует cwd/`MLREVIEW_HOME`;
  не отключать эти стражи. Архитектуру проверяет `tests/test_architecture.py`.

## Карта изменений

| Область | Код | Спецификации и проверки |
| --- | --- | --- |
| Контракты, находки, SQLite | `src/mlreview/core/` | task-spec, run-contract, findings-store, journal |
| Файлы, MLflow | `src/mlreview/adapters/` | files-adapter, mlflow-adapter; ручная проверка в `docs/manual-testing/mlflow-adapter.md` |
| Анализаторы | `src/mlreview/analyzers/` | analyzers и профильные спецификации; `tests/test_analyzers.py` |
| Метрики, экспорт ядер | `src/mlreview/metrics/` | metrics; `tests/test_metrics_kernels.py`, `tests/test_metrics_spec.py` |
| Семейства моделей | `src/mlreview/playbooks/` | playbooks, playbook-neighbors, playbook-trees |
| LLM, приватность | `src/mlreview/llm/` | llm; `tests/test_grounding.py`, `tests/test_llm_providers.py`, `tests/test_offline.py` |
| CLI / API / MCP | `src/mlreview/cli/`, `src/mlreview/api.py`, `src/mlreview/mcp_server/` | review, api, mcp-server и тесты соответствующего интерфейса |
| Приёмка, скорость | `benchmark/` | benchmark; `tests/test_benchmark.py` |

Имена в последней колонке без расширения обозначают документы в `docs/specs/`.
При изменении ядер метрик проверять также генерируемый экспорт. При изменении
анализатора проверять чистый пример и пример с дефектом, отсутствие обязательных полей.

## Команды и скиллы

Команды выполнять из корня активированным Python-окружением:

```bash
python -m pip install -e ".[dev]"       # минимальная разработка
python -m pip install -r requirements.txt  # extras MLflow/MCP и sklearn
python -m ruff check .
python -m ruff format --check .
python -m pytest -q
python -m mlreview --help
python -m benchmark
python -m benchmark --perf
```

Перед завершением изменения кода выполнить все три проверки Ruff/pytest, даже
если одна упала. Отдельно сообщать ошибки, пропуски необязательных интеграций и
недоступные зависимости. Не форматировать весь грязный репозиторий автоматически.
Бенчмарк запускать при изменении диагностик, численных алгоритмов или скорости;
гейт L1: Q1 ≥ 70%, Q2 ≤ 1, performance: 100 тыс. примеров ≤ 120 с.

Проектные скиллы находятся в `.agents/skills/`:
`mlreview-develop` — изменение поведения, `mlreview-check` — проверки,
`mlreview-docs-sync` — актуальность документации,
`mlreview-analyzer` — анализаторы и проверки плейбуков.

## Настройки и хуки Codex

`.codex/config.toml` задаёт настройки проекта, `.codex/hooks.json` — события,
`.codex/hooks/checks.py` — реализацию; поведение описано в
`docs/specs/codex-setup.md`. Хуки используют активный `python`, доступны в локальном
Codex с поддержкой hooks; для запуска из подкаталогов находят корень через Git.

После установки открыть новую сессию Codex в доверенном проекте и через `/hooks`
проверить и доверить новым хукам. Настройки не выдают доверие автоматически,
не меняют глобальную конфигурацию, модель или ограничения управляемой среды.

- `SessionStart`: снимок файлов для сравнения изменений этой сессии.
- `PostToolUse` после Bash/apply_patch: Ruff для изменившихся Python-файлов,
  включая изменения через shell; проверенные версии повторно не проверяются.
- `Stop`: если изменился код или конфигурация проверок — полный Ruff и pytest;
  напоминание о документации. Успешный результат кэшируется по содержимому,
  при ошибке возвращается обратная связь без бесконечного повторения Stop.
- Состояние — `.codex-state/` (игнорируется Git); архивы диалогов не читаются.
  Хуки ничего не форматируют, не устанавливают и не коммитят автоматически.
  Правило о диалогах — инструкция агенту, не полноценная файловая песочница.

## Web UI P0

`src/mlreview/web/` — опциональный FastAPI-сервер и bundled SPA;
`frontend/` — React/TypeScript/Vite, Node >=22.12. Контракт: `docs/specs/web-ui.md`.
Изменения серверного поведения проверяются `tests/test_web.py` с сетевыми стражами.
После изменений frontend выполнить из `frontend/`: `npm run format:check`,
`npm run build`, `npm test`; обновить собранные assets в `src/mlreview/web/static`.
При изменении сквозных сценариев — `npm run e2e` (Playwright Chromium, отдельный
временный workspace). E2E не отключает сетевые стражи pytest. Зависимости backend:
`python -m pip install -e ".[dev,web,web-test]"`; обычный CLI не требует web extra.
