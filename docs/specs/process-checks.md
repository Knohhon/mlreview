# Логические проверки процесса

Опора: FR-D06 (несколько изменений за раз, сравнение на разных версиях данных, многократное использование валидации — L1 · Must), FR-C04 (версия и хеш данных), B07 (сравнение на разных версиях данных), B11 (несколько изменений в одном эксперименте), S20 («менялись сразу три вещи»), X1.

Модуль `mlreview.analyzers.process`, группа `process`.

## Конфиг

Конфиг прогона (`config`) разворачивается в плоский словарь: вложенные словари — ключи через точку (`optimizer.lr`). Значения сравниваются как строки (`str`), поэтому `0.01` из YAML и `"0.01"` из параметров MLflow совпадают. Ключи сида — последний компонент ключа `seed`, `random_state`, `random_seed`, `rng_seed` или оканчивается на `_seed` — не считаются изменением.

## Проверки

| Проверка | Условие | severity |
| --- | --- | --- |
| `process.data_version_mismatch` | есть базовый прогон и `data_version` различаются, или версии совпадают / не заданы, а `data_hash` различаются | high |
| `process.multiple_changes` | есть базовый прогон, конфиги обоих непусты, изменено ≥ 2 ключей (кроме ключей сида) | medium |
| `process.seed_config_mismatch` | сиды одной стороны различаются не только ключами сида | medium |
| `process.validation_reuse` | хранилище знает ≥ 20 прогонов на тех же данных (тот же `data_hash`), включая текущий | medium |

## Ожидаемое поведение

- B1. Дано: кандидат `v2`, базовый `v1`, хеши разные · тогда `process.data_version_mismatch` high «сравнение на разных версиях данных: v1 → v2 — разница метрик может объясняться данными, а не моделью»; факты `baseline_version`, `candidate_version`, `baseline_hash`, `candidate_hash`; предложение — переобучить базовую конфигурацию на новых данных (различающий эксперимент).
- B2. Дано: версии одинаковые (или не заданы), хеши разные · тогда та же проверка: «сравнение на разных данных: хеш <база> → <кандидат> при версии <версия|не задана> — метка версии не отражает изменение».
- B3. Дано: версии разные, хеши одинаковые · тогда находки нет (данные совпадают).
- B4. Дано: изменены `loss`, `lr` и `augment`, `seed` тоже другой · тогда `process.multiple_changes` medium «в эксперименте изменено сразу 3 параметра: augment (none → flip), loss (ce → focal), lr (0.01 → 0.001) — эффект нельзя приписать одному изменению»; факты `changed` (число), `keys` (через запятую); предложение — абляция по одному параметру.
- B5. Дано: изменён один параметр или только сид · тогда находки нет.
- B6. Дано: ключ есть только у одного прогона · тогда он считается изменённым («нет» на месте отсутствующего значения).
- B7. Дано: сиды кандидата различаются ещё и `lr` · тогда `process.seed_config_mismatch` medium «прогоны по сидам кандидата различаются не только сидом: lr».
- B8. Дано: `prior_runs` = 19 (+ текущий = 20) · тогда `process.validation_reuse` medium «на одних данных (<хеш>) прошли ревью 20 прогонов — решения принимаются по одной валидации, риск переобучения на ней; проверьте итоговую модель на отложенной выборке»; при 18 других — находки нет.

## Деградация и ошибки

- E1. Дано: нет базового прогона · тогда пропуски `process.data_version_mismatch` и `process.multiple_changes` «нет базового прогона».
- E2. Дано: конфиг пуст у кандидата или базового · тогда пропуск `process.multiple_changes` «нет config у <кандидата|базового прогона>».
- E3. Дано: хранилища нет (`prior_runs` = `None`) · тогда пропуск `process.validation_reuse` «нет хранилища находок — история прогонов неизвестна (mlreview init)».

## Вне рамок

- Анализ кода пайплайна (B04, B10 — L2), десятки решений по одной валидации с падением на тесте (B09 — L2; здесь только счётчик прогонов).
