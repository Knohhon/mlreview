# Проектирование метрик

Опора: FR-M01 (диалог о контексте решения: цена ошибок, порог или ранжирование, калибровка, сегменты — L1 · Must), FR-M02 (библиотека метрик со свойствами задачи, обоснованием и ловушками — L1 · Must для 1–2 типов задач), FR-M03 (юнит-тесты метрик: тривиальные бейзлайны, вырожденные решения, бутстрап-шум, минимально различимый эффект — L1 · Must), FR-M04 (экспорт спецификации метрик как исполняемого кода — L1 · Must), FR-M05 (пользовательская метрика с теми же тестами — L1 · Should), FR-C01 (раздел `metrics:` спецификации), S01, B05 (accuracy при дисбалансе 1:50), NFR-03, NFR-05.

Пакет `mlreview.metrics`: `catalog` — описания метрик (данные), `kernels` — реализации на numpy, `library` — метрика для анализаторов, `advisor` — рекомендации по ответам диалога, `testing` — юнит-тесты метрик, `export` — генерация `metrics.py`.

## Раздел `metrics:` спецификации задачи

```yaml
metrics:
  primary: pr_auc                          # основная: по ней работают срезы и сиды
  secondary: [roc_auc, recall_at_k@50, ece]
  threshold: 0.5                           # порог для метрик по классам при output: probabilities
  context:                                 # ответы диалога (FR-M01)
    decision: ranking                      # threshold | ranking | probability
    budget_k: 50                           # для ranking: сколько объектов проверяют
    cost_ratio: 20                         # во сколько раз пропуск (недооценка) дороже ложной тревоги (переоценки)
    calibration: true
    large_errors: false                    # регрессия: крупные ошибки непропорционально дороже
    critical_segments: [language]
  custom:
    - {name: top50_toxic, path: my_metrics.py, function: top50, higher_is_better: true}
```

- Имя метрики — `имя` или `имя@параметр`: `precision_at_k@50`, `recall_at_k@50`, `top_k_accuracy@3` (k — целое ≥ 1, по умолчанию 10), `fbeta@2` (β > 0, по умолчанию 1), `pinball@0.9` (τ в (0, 1), по умолчанию 0,5).
- Метрика должна подходить к `task.type · task.output` (таблица ниже) или быть пользовательской из `custom`.
- Если раздела нет, метрики — как на L0 (`docs/specs/run-comparison.md`); если есть — `primary` и `secondary` заменяют их во всех анализаторах.
- Пользовательская метрика — функция `f(labels, predictions) -> float` из файла `path` (относительно файла спецификации): `labels` — метки (в multiclass — коды классов 0…C−1 в порядке колонок `prediction:<класс>`), `predictions` — предсказания (вектор или матрица вероятностей). `higher_is_better` (по умолчанию `true`), `bounded`: `high` (лучшее 1 на [0, 1]), `low` (лучшее 0 на [0, 1]) или нет.

## Библиотека (FR-M02)

| Метрика | Задачи (`тип · выход`) | Вход | Лучше | Ограничена |
| --- | --- | --- | --- | --- |
| `accuracy` | binary · labels/probabilities, multiclass · все | классы | ↑ | [0, 1] |
| `balanced_accuracy` | binary · labels/probabilities, multiclass · все | классы | ↑ | [0, 1] |
| `precision`, `recall`, `f1`, `fbeta@β` | binary · labels/probabilities | классы | ↑ | [0, 1] |
| `macro_f1` | multiclass · все | классы | ↑ | [0, 1] |
| `roc_auc`, `pr_auc` | binary · probabilities/scores | оценки | ↑ | [0, 1] |
| `precision_at_k@k`, `recall_at_k@k` | binary · probabilities/scores | оценки | ↑ | [0, 1] |
| `top_k_accuracy@k` | multiclass · probabilities/scores | оценки | ↑ | [0, 1] |
| `log_loss` | binary · probabilities, multiclass · probabilities | вероятности | ↓ | нет |
| `brier` | binary · probabilities | вероятности | ↓ | [0, 1] |
| `ece` | binary · probabilities, multiclass · probabilities | вероятности | ↓ | [0, 1] |
| `mae`, `rmse`, `median_ae`, `mape`, `pinball@τ` | regression · values | значения | ↓ | нет |
| `r2` | regression · values | значения | ↑ | нет |

Классы при `probabilities`: бинарная — `p ≥ threshold`, multiclass — argmax. У каждой метрики в каталоге — название, обоснование (когда она уместна) и ловушки (например, «accuracy: при дисбалансе константный предиктор получает долю мажоритарного класса»). `mlreview metrics list [--task <тип> --output <выход>]` печатает каталог.

## Диалог и рекомендации (FR-M01)

`mlreview metrics init --spec <путь> [--answers <yaml>] [--run <прогон>] [--write]`: вопросы задаются в терминале (если stdin — терминал и нет `--answers`); ответ по умолчанию — из спецификации (сегменты, `error_costs`: `low`=1, `medium`=3, `high`=10, отношение пропуск/ложная тревога или недооценка/переоценка). Без терминала и без `--answers` — ответы по умолчанию с пометкой. `--run` даёт долю положительного класса для правила дисбаланса. Вывод — рекомендации (роль, обоснование, ловушки) и раздел `metrics:` в YAML; `--write` записывает раздел в файл спецификации (заменяет существующий раздел `metrics:`, остальной текст и комментарии сохраняются).

Правила `advisor.recommend(spec, context, positive_rate=None)`:

| Задача | Решение | Основная | Дополнительные |
| --- | --- | --- | --- |
| binary | `ranking` (K) | `precision_at_k@K` | `recall_at_k@K`, `pr_auc` при дисбалансе (доля < 0,1), иначе `roc_auc` |
| binary | `threshold` | `fbeta@√r` (r — `cost_ratio`; при r = 1 — `f1`) | `precision`, `recall`; при вероятностях или оценках — `pr_auc` при дисбалансе, иначе `roc_auc` |
| binary | `probability` | `log_loss` | `ece`, `brier` (без дисбаланса), `roc_auc` |
| multiclass | `ranking` (K) | `top_k_accuracy@K` | `macro_f1` |
| multiclass | `threshold` | `macro_f1` | `balanced_accuracy`, `accuracy` |
| multiclass | `probability` | `log_loss` | `ece`, `macro_f1` |
| regression | r ≠ 1 | `pinball@τ`, τ = r/(1+r) | `mae` |
| regression | `large_errors` | `rmse` | `mae` |
| regression | иначе | `mae` | `rmse` |

Метрики, не подходящие к выходу (`ranking` при `labels`), заменяются ближайшими подходящими с пояснением. При `calibration: true` и `probabilities` добавляется `ece`. `accuracy` не рекомендуется при дисбалансе. Тип задачи без правил (multilabel) — рекомендаций нет, пометка «ограниченная поддержка».

## Юнит-тесты метрик (FR-M03, FR-M05)

`mlreview metrics test <прогон> --spec <путь> [--keep <метрика> --reason <текст>]` на метках и предсказаниях прогона (размер test — как у прогона) для каждой метрики спецификации (или метрик L0 без раздела):

| Тест | Что считается | Провал |
| --- | --- | --- |
| тривиальные бейзлайны | метрика у константных предсказаний: binary — доля класса 1 как вероятность (или мажоритарный класс), «всегда 0», «всегда 1»; multiclass — мажоритарный класс; regression — среднее и медиана | — |
| вырожденное решение | лучший тривиальный бейзлайн против границы | ограниченная ↑: ≥ 0,9; ограниченная ↓: ≤ 0,1 |
| бутстрап-шум | 95% CI метрики модели (1000 выборок, сид 0), полуширина | — |
| минимально различимый эффект | MDE = 2,8·√2·SE, SE = ширина CI / (2·1,96) — оценка для двух независимых моделей | — |
| отличает модель | модель лучше лучшего тривиального бейзлайна больше чем на MDE | нет |

`--keep` с причиной записывает в журнал решение «оставить метрику <имя>, несмотря на непройденные тесты: <причина>» (S01, ветвление); без рабочего пространства — ошибка с подсказкой `mlreview init`. Код возврата 0, если тесты выполнены (провал — не ошибка команды).

## Пригодность метрик в ревью (B05)

Анализатор `metrics.unsuitable` (группа `metrics`) запускает тест «вырожденное решение» для метрик задачи на метках кандидата, но только с бейзлайнами, зависящими от данных, — «константа мажоритарного класса» и «константа доли класса 1» (константа противоположного класса делает `recall` вырожденной всегда, а не на этих данных; это показывает `metrics test`): провал основной метрики — high, дополнительной — medium: «<метрика> вырождена на этих данных: <бейзлайн> получает <значение> — метрика не различает модели»; факты `metric`, `role`, `baseline`, `baseline_value`, `positive_rate` (для бинарной задачи); предложение — метрики из рекомендаций и `mlreview metrics init`.

## Экспорт (FR-M04)

`mlreview metrics export --spec <путь> [-o metrics.py]` пишет модуль на numpy: исходники реализаций метрик из `mlreview.metrics.kernels`, константы `TASK`, `THRESHOLD`, `PRIMARY` и функцию `compute(labels, predictions) -> dict[str, float]`; пользовательские метрики подключаются из своих файлов. Модуль не импортирует `mlreview`.

## Ожидаемое поведение

- B1. Дано: раздел `metrics:` с допустимыми метриками · тогда спецификация валидна; `primary` и `secondary` доступны в `spec.metrics`.
- B2. Дано: реализации `kernels` · тогда на случайных данных совпадают с эталоном (scikit-learn, если установлен; иначе — с формулами в тестах) до 1e-9: `roc_auc`, `pr_auc` (average precision), `log_loss`, `brier`, `accuracy`, `balanced_accuracy`, `precision`, `recall`, `f1`, `fbeta`, `macro_f1`, `top_k_accuracy`, `mae`, `rmse`, `median_ae`, `r2`, `mape`, `pinball`.
- B3. Дано: спецификация с `metrics:` · когда ревью · тогда `metrics.value` и `comparison.metric_delta` — по метрикам раздела, срезы и сиды — по `primary`.
- B4. Дано: ответы диалога (binary · probabilities, ranking, K=50, доля положительных 0,02) · тогда рекомендации `precision_at_k@50` (основная), `recall_at_k@50`, `pr_auc`; у каждой — обоснование и ловушки. Остальные строки таблицы правил — по тесту на каждую.
- B5. Дано: интерактивный диалог (ответы через stdin) · тогда вопросы печатаются, ответы по умолчанию — из спецификации; `--write` записывает раздел `metrics:` в файл, остальное содержимое файла сохраняется, файл остаётся валидной спецификацией.
- B6. Дано: метки с дисбалансом 1:50 и метрика `accuracy` · когда `metrics test` · тогда тест «вырожденное решение» провален: «константа мажоритарного класса получает 0.980»; `roc_auc` его проходит.
- B7. Дано: модель, неотличимая от константы · тогда тест «отличает модель» провален; для хорошей модели — пройден; печатаются CI и MDE.
- B8. Дано: пользовательская метрика в `custom` · тогда она проходит те же тесты, участвует в ревью и экспорте.
- B9. Дано: `--keep accuracy --reason …` · тогда в журнале решение со ссылкой на прогон.
- B10. Дано: экспорт · тогда сгенерированный файл исполняется без `mlreview`, и `compute` даёт те же числа, что библиотека.
- B11. Дано: спецификация `metrics: {primary: accuracy}` и метки 1:50 · когда ревью · тогда `metrics.unsuitable` high (B05); для `roc_auc` находки нет.

## Деградация и ошибки

- E1. Дано: неизвестная метрика, метрика не для этого выхода, плохой параметр (`precision_at_k@0`, `pinball@2`), повтор имени, порог вне (0, 1) · тогда спецификация невалидна с путём поля (`metrics.primary`, `metrics.secondary.1`) и списком допустимых метрик.
- E2. Дано: файл пользовательской метрики не найден, не импортируется или в нём нет функции · тогда ошибка с путём и причиной; функция вернула не число · метрика «не определена» в тестах и пропуск в ревью.
- E3. Дано: тип задачи classification/multilabel · тогда рекомендаций нет и пометка «ограниченная поддержка: в библиотеке нет метрик для classification/multilabel».
- E4. Дано: `--answers` с неизвестным ключом или недопустимым значением · тогда код 1 и сообщение.
