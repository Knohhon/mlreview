# Приёмочный бенчмарк L0–L1

Опора: раздел «Приёмочный бенчмарк» в `docs/MLReview-analysis.md` — дефекты L0: B01 (дубли train/test), B02 (временная утечка), B12 (регрессия сегмента); L1: B03 (утечка таргета через признак), B05 (неподходящая метрика), B07 (сравнение на разных версиях данных), B08 («улучшение» в пределах шума), B11 (несколько изменений в одном эксперименте); метрики качества Q1 (recall дефектов: L0 ≥ 50%, L1 ≥ 70%) и Q2 (ложные critical на чистый проект: L0 ≤ 3, L1 ≤ 1); NFR-06 (анализ прогона на 100 тыс. примеров без LLM ≤ 2 мин); FR-D01–D06, FR-M03; NFR-01 (scikit-learn — только в бенчмарке, не в пакете), NFR-03 (офлайн), NFR-05.

Каталог `benchmark/` в корне репозитория (вне пакета `mlreview`): проекты на датасетах, поставляемых с scikit-learn (сеть не нужна), линейные модели, контракты собираются через `build_run_contract` без трекера, ревью — `mlreview.analyzers.review.review`. Запуск: `python -m benchmark`.

## Проекты

| Проект | Датасет | Задача | Сегмент (испорченное значение для B12) | Базовый прогон | Доля B12 |
| --- | --- | --- | --- | --- | --- |
| `breast_cancer` | `load_breast_cancer` | `classification/binary · probabilities`, логистическая регрессия | `texture`: `rough`/`smooth` по медиане `mean texture` (`smooth`) | 1 признак | 0,3 |
| `diabetes` | `load_diabetes` | `regression · values`, линейная регрессия | `sex_group`: `a`/`b` по знаку признака `sex` (`a`) | 3 признака | 0,3 |
| `digits` | `load_digits` | `classification/multiclass · probabilities`, логистическая регрессия | `ink`: `heavy`/`light` по медиане средней яркости (`light`) | 16 признаков | 0,5 |

Время у примеров синтетическое (в датасетах его нет): случайная перестановка с сидом задаёт порядок, колонка `ts` — дата с шагом в час. Спецификация каждого проекта: `split_strategy: temporal`, `time_column: ts`, сегмент из таблицы. Кандидат — модель на всех признаках; базовый прогон — та же модель на первых N признаках датасета (слабее, чтобы у кандидата был запас роста средней метрики). Признаки стандартизуются по train.

## Версии проекта

Конфиги прогонов: базовый — `{features: N, C: 1.0, scaler: standard, class_weight: none}`, кандидат — тот же с `features: all` (одно изменение). Версия данных — `<проект>-v1`.

- **clean** — временной сплит: последние 30% по времени — test.
- **B01** — clean, плюс 5% строк test (с округлением вверх) скопированы в train с новыми id, как в каталоге дефектов. Копии сохраняют время строк test, поэтому версия B01 ловится и временной проверкой; это следствие дефекта, а не ложное срабатывание.
- **B02** — случайный сплит 70/30 при той же спецификации `temporal`.
- **B12** — clean, но на испорченном значении сегмента предсказания кандидата заменены предсказаниями базового прогона, и у доли «Доля B12» примеров этого значения они перемешаны между собой (перестановка с сидом). Вне сегмента остаются предсказания кандидата. Так сегмент становится хуже базового прогона, а средняя метрика растёт.
- **B03** (`breast_cancer`, `diabetes`; для multiclass проверка сильных признаков на L1 не выполняется) — clean, плюс в `examples` признак `leak` = метка + шум (σ = 0,01 стандартного отклонения метки, сид 4).
- **B05** (`breast_cancer`) — в спецификации `metrics: {primary: accuracy}`, а в оцениваемых примерах остаются все отрицательные и ⌈отрицательных / 50⌉ первых по id положительных (дисбаланс 1:50); модели — как в clean.
- **B07** — базовый прогон из clean, но с версией данных `<проект>-v0` и `examples` без каждой десятой строки train (другой хеш данных).
- **B08** — кандидат и базовый — одна модель со всеми признаками, отличается только `C` (1,0 и 1,05; для регрессии — `alpha` гребневой регрессии 1,0 и 1,05); по 3 сида на сторону, сид — бутстрап-выборка строк train (сиды 11–13).
- **B11** — clean, но конфиг кандидата отличается от базового ещё и `C`, `scaler`, `class_weight` (четыре изменения).

Ревью каждой версии — кандидат против базового прогона той же версии (B08 — с сидами). Модели для clean, B03, B05, B07, B11 и B12 общие (один сплит) и кэшируются на время процесса.

**Найден:** B01 — есть `data.split_duplicates` уровня `critical`; B02 — `data.temporal_leak` уровня `critical`; B12 — `slices.segment_regression` по испорченному значению сегмента; B03 — `data.strong_feature` по признаку `leak`; B05 — `metrics.unsuitable` по `accuracy`; B07 — `process.data_version_mismatch`; B08 — `seeds.within_noise` уровня high или medium (улучшение по какой-то метрике в пределах шума по сидам); B11 — `process.multiple_changes`.

## Производительность (NFR-06)

`python -m benchmark --perf [--n 100000]` строит синтетический прогон бинарной классификации (`n` примеров test и столько же train, 20 признаков, два сегмента, время), базовый прогон и сравнивает их полным ревью без LLM; печатает время сборки контрактов и ревью; код 0, если ревью уложилось в 120 с. Бутстрап ROC AUC считается через веса повторов по один раз отсортированным оценкам (O(n) на выборку) — значение то же, что у ROC AUC на выборке с повторами.

## Ожидаемое поведение

- B1. Дано: все проекты и применимые к ним версии · когда `run_benchmark()` · тогда для каждой версии с дефектом — признак «найден», для clean — число critical-находок; Q1 = найдено / всего дефектов, Q2 = среднее число critical на clean.
- B2. Тогда Q1 ≥ 70% и Q2 ≤ 1 (гейт L1; гейт L0 — 50% и 3); целевое на текущем наборе — все 21 дефект найдены и 0 critical на clean.
- B3. Дано: версия B12 · тогда основная метрика кандидата в целом не хуже базового прогона («регрессия сегмента при росте средней метрики»).
- B4. Дано: повторный запуск · тогда результаты идентичны (NFR-05).
- B5. `python -m benchmark` печатает таблицу проектов и версий с результатом и строку Q1/Q2; код 0, если гейт L1 пройден, иначе 1.
- B6. Дано: `--perf` · тогда время ревью синтетического прогона и код 0 при ≤ 120 с (NFR-06); быстрый бутстрап ROC AUC совпадает с ROC AUC на выборке с повторами до 1e-12.
